# Plan CORE2: more work off the game thread (oracle, 2026-11-08, nds1 71a457148)

## Today
- Core 0: game thread (pm_main.c:832): walk, geometry, GPU submit, texture decode, game logic.
- Core 1 (system core, APT_SetAppCpuTimeLimit 80, retry 79, 30 on HOME/sleep, switch cpulimit=; pm_log.c:1203-1216): audio control (pm_audio.c:112), audio mixer (pm_au2.c:177), log writer (pm_log.c:996), log sink (pm_log.c:1231), flash/save (pm_flash.c:86), watchdog (pm_wdog.c:154).

- N3DS: osSetSpeedupEnable(true) (pm_main.c:769); no thread on core 2.
- Console cost (O3DS XL, runs 25158/25044): mac_01 ft 32.4-32.6 ms, gbi 29.7-36.4, oh 7.9-12.5; logic about 3.3 ms (frame_budget.md). The game thread is walk-bound.

## Candidates (ranked by console gain against risk)
1. Audio one step ahead (done, CORE2-1). The audio job of step N (kicked at the main nuGfxTaskStart) used to be joined after the walk (pm_main.c), at the retrace call and at step_game_loop. Old O3DS logs (build 1462, ftp_170b/170c, audiostat) show the cost: 6-29 of 300 steps waited after the walk, 9-27 ms each (job max 30-100 ms), 135-800 us per step on average. Now the job is joined only at the next snd_* call of the game (pm_audio_gate.c), at the next kick, and at drain/sleep/exit. Boundary audit (nm of the elf, all src and 3ds/src files): game code reaches the engine only through the 66 snd_* functions of snd_interface.c; no game file reads gSoundManager, gBGMPlayer*, gAuAmbienceManager, gSoundGlobals; the engine calls no game code (no callback registered). So the order of engine and game accesses is unchanged.
2. Walker thread on N3DS core 2: game logic of frame N+1 in parallel with the walk of frame N. The walker owns nd_ws, pm_gpu, pm_tex, the model cache, C3D and the GX queue; the game thread calls no pm_gpu_* (HUD, menu present, GREY, shots move to the walker). Handoff: the finished gfx task (gbi_task, pm_nusys.c) into a 1-deep queue. Det walks in series. Gain up to about 3-12 ms per frame on N3DS. Not on O3DS (walk ~30 ms, core 1 at most 80% shared). Risk high: every game buffer the list points to and the game rewrites in place (effect vertex buffers, ent_dynlist, sprite records, G_PM_SPR reads) must be found first.
3. Texture decode/staging worker: 0.02-0.4 ms per frame steady; helps map-change hitches only. Only if a console hitch measurement points there.
4. Model cache builds, log formatting: no gain (part of the walk; logging is off in prof mode).

## CORE2-2 design: the walker thread on N3DS core 2

### Premise check
- In code: PASS. The N64 game already lets the RSP read a list while the CPU runs the next frame, so the data of a list is double-buffered (gDisplayContext[gCurrentDisplayContextIndex]: list words, matrix stack, imgfx vertex buffers). The census (below) finds 0 to 1 rewritten entries per frame out of 110 to 400 walker-read pointers, in town walk, battle, pause and an effect scene. Game-thread GPU calls outside the walker are a finite list (Ownership).
- On the console, still open (prof line `prof core2 probe`, pm_phase.c c2_probe): (a) whether the N3DS lets the game create a thread on core 2; (b) the N3DS frame cost. There is no N3DS prof run in the bench database. At 30 fps the thread gains time only when the N3DS frame is over 33.3 ms. The gain is at most the logic plus the list build of a frame (about 7.7 ms on the O3DS, frame_budget.md; about a third of that on the N3DS). Under 33.3 ms it gains only in 60 fps mode (interp). CORE2-3 starts after one N3DS prof run (spot_mac01_prof, spot_iwa10_prof) shows a created core-2 thread and ft_ms over 33.3 ms (or the user wants 60 fps).

### Census (switch c2haz, nd_c2haz.c; benches c2haz_mac01, c2haz_battle, c2haz_pause, c2haz_nok11)
Every pointer the walker resolves (ptr_of, plus the pointer words of G_PM_REC, G_PM_SPR and G_PM_ENT records, plus the task list) is hashed (first 64 bytes) when the walk reads it. Hashes are checked again at the first task of the next drawn frame, after the logic and the list build of that frame. One `c2haz new` line per changed address; a `c2haz sum` line every 60 frames. Addresses are named from the elf (nm). Result on 4ebd427f3 plus CORE2-1:
1. gCameras[1] + 0xA0 (Camera.vp; also vpAlt), G_MOVEMEM viewport, rewritten in place (battle frame 158). FIXED (CORE2-3a f976f77e6): the 10 camera gSPViewport sites pass PM_VP(&cam->vp), a copy made at list build (pm_nusys.c pm_vp_snap, a 32-entry pool per display context).
2. Heap display lists (port malloc heap 0x327bxxxx, G_DL). NOT a game hazard: census v2 hashes again after each walk, and these were the walker's own cache lists (nd_ent.c flattened lists, nd_dlc/nd_shape copies) that the walk rewrote after their first read. No deferred free is needed: game code never allocates from the port malloc heap (src/ has no malloc). The N64 heaps are bss.
3. Frame buffers: the captures (pm_cfb_capture_prev*, pm_gpu_read_frame, pm_gpu_grab_prev) already run inside the walk (nd_rect.c, nd_tex_set.c). FIXED (a7c749d94): the pause filter (gfx_transfer_frame_to_depth) reads the walked frame buffers on the game thread, so it starts with pm_walk_drain("cfb").
4. Load writes: ROM reads, decodes, map loads and mode changes write memory that the last walk read. FIXED as drain points (CORE2-3b c0ab8296f): pm_walk_drain at nuPiReadRom (game thread), before a yay0 decode, and at the load_map_by_IDs and set_game_mode wraps. Census after the fix: no game address. One-time addresses after a map or battle entry remain; they are walker cache Gfx lists in the port heap. Drains happen 419 to 2725 times per 300 frames, because sprite raster ROM reads also happen at steady state. A drain that always waits would remove most of the overlap, so 3c needs a range-aware drain: wait only when the write range overlaps a page that the walk in flight reads (a page bitmap built by the walker, as the census table does).
5. False positives: G_PM_REC words that are counters, not pointers (nok_11: plan, slots, scm, c2_tab). An op 0d line is a hazard only when the word is a pointer field of the record.
Not seen by the census (code audit): the native caches (model, entity, sprite, texture) after their first build. They are keyed by address and owned by the walker, and their invalidations become messages. The sprite raster caches (PlayerRasterCache, sprite.c pm_tex_sprite_range) are rewritten on a raster miss. They showed no change in a 240-frame town walk; the deferred-free rule does not cover them, so a cache slot is not reused until the walker has finished the frame that read it.

### Ownership
- Walker thread (core 2, priority 0x2F): nd_ws and all nd_* walker state, pm_gpu (C3D context, command buffers, GX queue, vertex ring), pm_tex (texture cache, VRAM), the model, entity and sprite native caches, C3D_FrameBegin/End and present, shots, grabs and captures, depth reads (pm_gpu_depth_at), HUD and menu present (pm_gpu_hud, pm_gpu_menu_*, pm_gpu_footer), stereo eye walks, interp key draws.
- Game thread (core 0): logic, list build into the display context, the audio kick and the snd_* gate (CORE2-1), and the queue push.
- Game-thread calls that become messages, applied in order before the next walk: pm_tex_invalidate (pm_os.c nuPiReadRom, pm_map.c decompress, background_gfx.c pause side copy, pm_main.c captures), pm_tex_sprite_range (sprite.c), pm_gpu_want_prev (encounter.c), pm_gpu_menu_draw and shot requests (pm_options_ui.c, pm_warp.c, debug bursts), and display mode changes (wide, stereo, fps).
- Read-only counters the game reads for logs (pm_tex_used, pm_gpu_pf_read, C3D_FrameCounter): read as relaxed words. They are not a hazard.

### Handoff
nuGfxTaskStart(swap) pushes one frame {background list, main list, cfb target, frame number, swap/stereo/key flags, the message block} into a queue of depth 1 and returns. Before the push of frame N+1 the game waits until the walker has finished frame N. So the display context of frame N is reused only after its walk (the N64 rule). Drain (wait until the walker is idle): map, battle and area loads, save, HOME, sleep, exit, pause capture, warp and tour, depth read. Det: the push waits for the walk at once (a serial walk), so det stays byte-equal.

### CORE2-3 steps (after the console premise)
3a. Walker side (done): nd_wq.c, pm_wq_post (a message; serial: runs at once) and pm_wq_call (drain, then run). Game-called entries of pm_gpu.c and pm_tex.c are wrappers around static bodies (begin, end, drew, menu present and dirty, shots, want_prev, depth_at, init, tex_invalidate, tex_sprite_range). The task walk (gbi_task), the key frame and the frame end (pm_main.c wq_frame_end) are posted, and C3D_Fini is called through pm_wq_call. The bottom-screen console (pm_gpu_ui.c: hud, footer, menu text) is not walker state; the log sink thread already writes it. Switch c2own logs an owned entry (pm_gbi_run, read_frame, grab_prev, cap_state, begin_wait, eye) that runs outside the walker side: none in the 4 census scenes.
3b. Hazard fixes (done): camera viewport copy (f976f77e6), load drain points (c0ab8296f), pause filter drain (a7c749d94). Open: range-aware drains (pm_walk_drain waits only when the write overlaps a page the walk in flight reads).
3c. Superseded by row_CORE2C (oracle 2026-11-08): the walker stays on core 0 (main thread), the logic thread moves to core 1 (O3DS) or core 2 (N3DS).
3c-1 (done, CORE2C-2): the queue in nd_wq.c. One ring of copied messages (32 entries of 32 argument bytes); a frame (PmFrame, pm_port.h: background task, main task, colour buffer, flags) is one entry, depth 1 (the push waits while a frame is queued). pm_wq_call and pm_walk_drain wait until the queue is empty (pm_wq_idle). The walker reads the colour buffer of the frame (pm_walk_cfb), not nuGfxCfb_ptr. The background task always goes with the main task (also with interp). One thread: a post or a push runs the queue at once (the serial order; det keeps it in 3c-2).
3c-2 (done, CORE2C-3, pm_logic.c): the logic thread (core 1 O3DS, core 2 N3DS, priority game + 2, 64 KB heap stack). The frame loop hands one command per pass (LG_IDLE retrace, LG_STEP, LG_SKIP; pad state latched into the command) and walks every finished step (pm_lg_show), so the logic of step N+1 runs while the walker draws N. The logic posts frame begin, the frame and the step end; the tail (frame number, warp and tour, fxtest, script dump) runs on the logic. The draw decision waits for the retrace flag the logic publishes before each retrace call (pm_nusys.c). 60 fps (CORE2I): the logic builds step N+1 while the walker draws the lerp frame and the key frame of N. The key frame is a queue message (PmKey, the task list taken by the logic at the step end, posted after the tail; pm_lg_show_keys on the idle pass walks it). The replacement table (rtab and repl, pm_interp.c) is read by the walker through pm_interp_find, so the logic writes it (pm_interp_lerp) only after pm_wq_frame_slot: the frame and key frame before are walked (the wait runs the queue up to them, not the begin entry of the next step, which would pull a vblank). Serial (inline on the game thread): det, phase and census timers, fsplit, dcsum, and the prof sample frame (pf_arm stops the logic first). The menu, frame advance hold, HOME, sleep and exit stop the logic at a step boundary (pm_lg_quiesce). Every game-thread wait runs the queue for a blocked logic thread, so a drain or frame push inside a step finishes. c2haz with the logic thread checks at the frame push (nd_c2_push). Prof line `core2`: lgms (logic ms per step), wwait (walk wait ms per drawn frame), ser, core, stk. Open: range-aware drains; the game reads "ever" one frame late (boot fallback only).
