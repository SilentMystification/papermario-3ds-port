# Row AZT: fast Azahar access for any agent (parallel slots, warm restart, test lists)

## Goal (user, 2026-11-06)
Azahar testing is the main bottleneck. Today: one global mutex (run_azahar.ps1 `Global\pm_azahar_run`), one shared sdmc (%APPDATA%\Azahar\sdmc), a cold Azahar start per test (about 12.6 s to the first marker). With 5 agents, runs wait in line. Target: any agent gets a slot fast, and a test on an already running build starts in seconds.

## Rows (one commit each, in this order)
AZT-1 PARALLEL SLOTS: Azahar portable mode (a `user` folder next to azahar.exe makes it use that folder for config and sdmc). Make N slot copies of C:\Program Files\Azahar (N = 3 default, set by an env var) under build3ds/azslots/slot<k>/ (copy once, gitignored), each with its own user/ (qt-config.ini copied from the current one, its own sdmc). run_azahar.ps1: replace the one mutex by a slot pool (named mutex per slot `Global\pm_azahar_slot<k>`, take the first free one, wait only when all are busy); all paths ($exe, $sd, qt-config.ini, options.ini, log.txt, shots) come from the slot. The options.ini guard (UI1a) and the budget work per slot. First verify portable mode: one run in slot 1, its log appears in slot1 sdmc, not in %APPDATA%. Gate: 3 scenarios started at the same time on 3 slots all pass their log checks, with no shared file.
AZT-2 WARM RESTART: keep a slot's Azahar open after a run (env or switch `-Keep`). The next run on that slot writes the 3dsx and debug3ds.txt into the slot sdmc and restarts emulation (Azahar Emulation > Restart hotkey, sent to that PID's main window; read the hotkey from the slot qt-config.ini). Verify by log: a new boot line with the new build number. If the restart fails or the window is gone, fall back to a cold start. An idle Azahar closes after 10 min. Gate: second run on the same slot reaches its first marker at least 3 s sooner than a cold start (log time stamps).
AZT-3 TEST LIST IN THE GAME: a debug switch `testlist=<file>` (file in sdmc): after each scenario's until-line the game writes a marker `testlist: done <n>`, reads the next line (a debug switch string), resets the game state the same way the boot path does for a warp (pm_warp.c live warp path, story, pos, padscript, shots), and runs it. azt.ps1 accepts several scenarios (`azt.ps1 a,b,c`) and runs them as one list on one start, splitting the log per scenario for the checks. Gate: a 3-scenario list (spot_mac01_pic, spot_mac00_pic, spot_sbk56_pic) passes each scenario's checks on one start, and the total time is less than 3 cold starts.
AZT-4 bench.py: `bench.py run` takes `--lane` and a list of benches (uses AZT-3), so agents stop calling azt.ps1 by hand for lane builds. Update docs/handoff/test_catalog.md in place (slots, -Keep, lists).
