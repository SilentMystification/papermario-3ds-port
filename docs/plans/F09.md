# F09 plan (planning only, 2026-10-18)

Rules: 3ds/AGENT_RULES.md. Each slice adds at most 10 KB of code. Model: sonnet per slice.

## Facts (from the code)
- include/variables.h:131-135: in the US build `gCurrentLanguage` is `#define 0`. Only VERSION_PAL has the variable.
- The only call site of GAME_MODE_LANGUAGE_SELECT (12) is src/state_title_screen.c:383-388, under `#if VERSION_PAL`.
- 162 files in src/ have `VERSION_PAL` blocks (msg.c 5, msg_draw.c 4, filemenu, pause, battle menus, effects).
- The US ROM has English text only. German, French and Spanish text exist only in the PAL ROM. assets/ has only `us`. The PAL decomp is near complete (ver/pal/asm has only header.s).
- 3ds/CMakeLists.txt builds with `VERSION_US` and `VERSION=us` (lines 13-14) and assets from `${DECOMP}/assets/us` (line 25). src/filemenu/filemenu_selectlanguage.c is not in the build list.

## Scope decision (for the user)
- Option A: US build only. No language select. Close F09 as `n/a in US build`. Cost 0.
- Option B (recommended if the user wants languages): a second build target `VERSION_PAL` from a PAL ROM the user owns. The PAL build has the decomp language select with EN, DE, FR, ES. No new game code: the decomp has it. The US build stays as it is.
- Option C: mix US code with PAL text. NOT recommended: message ids, font and layout differ by version. This is a hand-written stand-in and breaks the no-stub rule.
Write the question in 3ds/QUESTIONS.md. Do not start F09-2 before the answer and the PAL ROM.

## Conflicts with the graphics rows
- F09-2, F09-3, F09-4, F09-6 touch build files, asset scripts and port tables only. No conflict with B1-B6, F08, V10, V13. They can start before S28 (after the user answer).
- F09-5 compares text pictures. B1-B6 and V10 can change texrect and box draws. Take the PAL golden references after those rows.
- PO3 (docs/plans/PO3_row.md): no conflict. PO3 work applies to both builds by the same port files.
- The PAL build doubles the test cost of every later graphics row only if the user wants both builds kept equal. Proposal: golden checks on US only, PAL smoke at milestones.

## Risks
- The user must give a PAL ROM. No ROM means option A.
- The port has per-version generated tables (ROM remap, map restore, data layout). Each one must be generated again for PAL. A missed table gives wrong ROM reads (unmapped faults).
- PAL fonts and the menu layout differ (VERSION_PAL blocks in msg_draw.c, filemenu). Visual faults show only in the PAL build.
- 50 Hz timing (F09-6).
- Save files: the PAL save layout can differ from US. Use a separate save name for the PAL build.

## O3DS cost (estimate, not hardware)
- CPU: the same as the US build. The language only selects a message bank. No per-frame cost.
- Load: German and French texts are longer. Text boxes can draw more glyphs. The cost is below 0.1 ms per frame.

## Memory estimate
- Code: about +4 KB plus filemenu_selectlanguage.c (325 lines, about 3 KB of code).
- Data: the PAL ROM holds 4 message banks. The US msg sources are 2.0 MB (assets/us/msg). Estimate the PAL message data at 3 to 4 times the US bank in the ROM file. If the port keeps message data resident in RAM, this is too much for the O3DS (spare about 4.7 MB, docs/MEMORY_BUDGET.md). Measure in F09-3 how the port reads messages (resident or from SD). If resident, keep only the bank of the current language resident (decomp loads one bank per language).
- The US build: 0 B change.
