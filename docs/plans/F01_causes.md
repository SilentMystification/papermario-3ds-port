# F01 causes: kmr_23, tst_12, nok_01 (read-only analysis, 2026-10-18)

Method: read-only. Sources: docs/HISTORY.md (lines 945-953, 1041, 1133, 1198), tails of 3ds/logs/f02_kmr_23.txt, 3ds/logs/s25_tourcsv_run_m03_129.txt, 3ds/logs/v09_nok.txt, the decomp source, and `git show` of shelf/v09-nok01 (two debug logs, not used as proof). No build. No Azahar run.

## 1. kmr_23 (curtain callback)
- Failing call: `gCurtainDrawCallback()` at src/curtains.c:279 calls `func_80240DA4_9087D4` (src/world/area_kmr/kmr_23/npc.c:404). Its first read is `evt_get_variable(nullptr, MV_EndChapterDataPtr)`, then `data->unk1E`. The tour reports the fault on the NEXT map (iwa_00, iwa_01 or iwa_02) because the tour lags one map.
- Likely cause. npc.c:98 sets the callback. The real exit script (kmr_23/main.c:17-26) calls `GotoMapSpecial`, then `FadeOutMusic`, then `N(func_80240010_907A40)`, which runs `set_curtain_draw_callback(nullptr)`. These calls do not block, so on the real exit the callback is cleared in the same frame. The tour warp leaves the map after 40 frames without that script. The pointer stays set. The map variable `MV_EndChapterDataPtr` is zero after the next map loads, so `data` is NULL. The N64 reads address 0 without a fault (low RDRAM is mapped). The 3DS port treats it as an unmapped access. `initialize_curtains()` (src/curtains.c:221) runs only at startup (state_startup.c:67, main_loop.c:312). Evidence: `warp=iwa_01:0` alone is clean (HISTORY 952). Same fault in 3 tours.
- Fix at the root: the tour or warp harness must leave a map the way the game does. Either (a) the tour runs the real exit of kmr_23 (entry 4 or the end of the script), or (b) pm_warp.c calls the game function `set_curtain_draw_callback(nullptr)` (or `initialize_curtains()`) before each warp. This resets game state in the harness. It is not a guard around the faulting read. Do not edit the decomp callback. Do not add a NULL check.
- Files: 3ds/src/pm_warp.c (tour and warp transition). No decomp file.
- Check: run the tour chunk that holds kmr_23 and its neighbours with `-Turbo -Smoke -FaultStop`, `partner=1 ptrcheck`. Expect 0 unmapped. Needs Azahar. Confirm the cause first with `warp=kmr_23:0` followed by `warp=iwa_01:0` in one run (HISTORY says nobody ran a normal exit).

## 2. tst_12 (cut map)
- Failing call: `floating_flower_main` at src/effects/floating_flower.c:31 (`part->type = type`). `general_heap_malloc` (line 29) returned NULL. The `ASSERT` on line 31 does not stop the port. 28410 faults, one PC.
- The earlier HISTORY note (line 953) says `evt_handle_loop` stores the variable id as the count. The source does not agree. `evt_handle_end_loop` (src/evt/evt.c:69-75) reads the variable when the stored id is below -10000000, so `Loop(LVar5)` counts the value of LVar5. By hand: LVar5 = 200 / raw(LVarF) + 1. `LVarF` holds a fixed-point encoded float of about -22.5 (raw about -2.3e8), so the integer divide gives 0 and LVar5 = 1. The loop is not the flood. This hand calculation is not verified.
- Likely cause (unproven): the endless part of the script is `Label(0) ... Wait(LVarF) Goto(0)` (src/world/area_tst/tst_12/main.c:46-54). `Wait(LVarF)` takes the raw value of `LVarF`. A raw value of 0 makes `evt_handle_wait` return at once, so the script never yields. Each pass makes one effect. The 96 effect slots fill. Allocation fails and the NULL write follows. A large negative raw value would wait about 2.3e8 frames and would not flood. So the real sign and size of `LVarF` decide. The bounds come from fixed numbers in `Exec` calls of EVS_Main (main.c:63-76), so the result does not depend on the tour state.
- If the flood is real in the decomp logic, the same code fails on the N64 (the map is unreachable in the game). Then the fault is a decomp defect of an unused map, not a port defect.
- Fix at the root: measure first, then decide. Do not guard. If the port evaluates `Div`, `DivF`, `Add` or `Wait` on fixed-point locals differently from the N64 (`evt_handle_divide`, `evt_handle_divideF`, the local branch of `evt_get_variable`), fix that function. If the port matches the N64, record the map as an N64-identical fault and drop tst_12 from the tour list (list change only, no game change).
- Files: src/evt/evt.c (read `evt_handle_divide`, `evt_handle_divideF`, `evt_handle_wait`), 3ds/src/pm_warp.c (tour list, only if the map is dropped).
- Check: Azahar run `warp=tst_12:0 -Smoke` with a temporary switch-gated log (not committed) of LVar5, raw LVarF and the count of `PlayEffect` calls in the first 10 frames. Needs Azahar.

## 3. nok_01 (`au_syn_begin_audio_frame`, engine.c:488, unmapped access)
- Failing call: src/audio/core/engine.c:488 `au_syn_start_voice_params(i, voice->busID, voice->instrument, ...)`. The faulting pointer is `voice->instrument`. Tour crash stacks (s25_tourcsv_run_m03_129.txt, v09_nok.txt): `au_syn_begin_audio_frame` engine.c:488 or 489, lr in `au_bgm_player_update_playing` at bgm_player.c:1250, 1318, 1328 or 1329. About 250 fault hits per run. The tour reports the map one early (nok_03 in the first tour).
- Evidence for the pointer: bgm_player.c:1305-1306 (`note->ins = track->instrument; ... - note->ins->keyBase`) reads through `track->instrument`. `au_bgm_player_initialize` sets it to `NO_INSTRUMENT` (-1, src/audio.h:14) at line 710. Only command F5 (`au_BGMCmd_F5_UseInstrument`, line 1735) changes it. 3ds/logs/v09_nok.txt holds 13 lines `V09DIAG track 0 song 81 patch 0 ptrk 0xe72e7c` from an older diagnostic of the stopped agent. They show track 0 of song 81 starting notes with `patch 0`, so F5 never ran on that track. (The shelf branch has a different log format. Both are unverified and are not proof.)
- Likely cause: a BGM track plays notes before its F5 command has set an instrument. So the track data the player reads is not the real song data, or the read position is wrong. Candidates, in order:
  1. The player starts on a BGM file that is not (fully) loaded or is zero filled. `au_read_rom` (engine.c:1366) goes through `nuPiReadRom` and `pi_read_raw` (3ds/src/pm_os.c:280-326). Zero fill happens there for ranges in `pm_rom_drop` and for reads past the end. The audio ranges (ROM 0xF00000 and up) are in `pm_rom_keep`, so this is unlikely. It is not proven for song 81 or for its bank files.
  2. A race. The game thread loads a new song (`au_load_song_files`, engine.c:680-735: ROM read, `au_swap_bgm_file`, `au_load_aux_bank`, then `au_bgm_player_initialize`) while the audio thread runs `au_bgm_player_update_playing` on the same player. On the N64 the audio thread has higher priority and runs at fixed points. The tour changes the map every 40 frames in turbo, so song changes come fast. A standalone `warp=nok_01:0` or `nok_03:0` (300 frames) is clean. That fits a timing fault.
  3. A double swap or a stale swap state in `au_swap_bgm_file` after a song reload (`au_reload_song_files`, engine.c:741).
  Not decided. No evidence tells 1, 2 and 3 apart.
- Fix at the root: find which candidate holds, then fix that cause. For 2: the port audio thread hand-over (`pm_au_thread_yield`, 3ds/src/pm_audio.c:126 and pm_os.c:82) must match the N64 ordering. For 1: the ROM remap. For 3: the swap. No `if (instrument == NO_INSTRUMENT) return` guard.
- Files: 3ds/src/pm_audio.c, 3ds/src/pm_os.c (audio thread, `nuPiReadRom`). src/audio/core/engine.c and src/audio/bgm_player.c only for temporary switch-gated logging.
- Check (needs Azahar): repeat the failing tour chunk (the chunk of 40 that holds area 6 map 2, nok) with a temporary log at `au_load_song_files`, `au_bgm_player_initialize`, F5 and the first note-on of track 0 (thread id, frame, song id, `bgmFile`, first 16 bytes of the track read position). One failing run shows whether the file is zero (1), whether load and update overlap in time (2), or whether the bytes are wrong (3). Then run `warp=nok_01:0` with a second song change inside the run to try to reproduce the fault outside the tour.
