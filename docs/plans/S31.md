# S31: crash screen and debug output (Q5)

Read-only analysis. Nothing was built. Azahar was not run.

## Verdict: (b)
The H02 port handler is enough. The three shims stay empty. The real decomp crash screen cannot run on the 3DS without new port code. The debug output has no use on the 3DS.

## Evidence
Decomp files: `src/crash_screen.c` (11699 bytes, 365 lines), `src/is_debug.c` (2626 bytes). Both are NOT in the CMake link list. The shims are `crash_screen_init`, `is_debug_init`, `load_obfuscation_shims` in `3ds/src/game_stubs.c` lines 17-19, and `crash_screen_set_draw_info` in `3ds/src/pm_later.c` line 6.

### Debug output (is_debug.c)
- `is_debug_print` writes text to the IS-Viewer 64 cartridge buffer at physical address 0xB3FF0000 with `osEPiReadIo` and `osEPiWriteIo`.
- This is a hardware device of a development cartridge. The 3DS has no such address. `nuPiCartHandle` in `3ds/src/pm_os.c` is a null pointer. The port has no `osEPiReadIo` or `osEPiWriteIo`.
- `is_debug_init` writes the "IS64" magic. Without the device nothing can read the output.
- Only 6 `osSyncPrintf` call sites exist in `src/`: `Pipe.inc.c` line 83 and 5 in `world/dead/area_flo` (dead code). `printf` in the game is not called from live code.
- To use it, the port would need to redirect `_Printf` output to `pm_log`. That is new port code with no value: `pm_log` already writes log.txt, crash.txt and the live socket.

### Crash screen (crash_screen.c)
What it needs, and what the port has:
- Fault hook: `osSetEventMesg(OS_EVENT_FAULT)` and `OS_EVENT_CPU_BREAK`, `osStopThread`, `crash_screen_get_faulted_thread` read the N64 thread queue. The port has none of these. `osCreateThread` in `pm_os.c` only starts the audio thread and ignores the others (no stack, no priority, no scheduler).
- The data it prints is the MIPS context (`ctx->pc`, `sr`, `badvaddr`, registers at, v0, a0..., f0..f31 through `__OSThreadContext`). The faults of the port are ARM faults. A MIPS context does not exist. The screen would show nothing true.
- Framebuffer: it writes RGBA5551 pixels to `frameBuf | 0xA0000000` (KSEG1) and calls `osViSwapBuffer`. On the port `osViSwapBuffer` only stores a pointer (`pm_os.c` line 56). `crash_screen_init` also computes the buffer from `osMemSize` (4 MB N64 heap on the port). The 3DS screens are GPU framebuffers in BGR formats, so the real draw code needs a new blit path.
- Font: `gCrashScreenFont` is 64 words (256 bytes) and `INCLUDE_IMG` needs the asset tool. It would link.
- Threads: it needs its own thread with a 0x800 byte stack. libctru has no hook to run it on a fault. The H02 handler runs in the faulting thread context (libctru exception handler, own 16 KB stack each).
- Size of the real code: 11699 bytes of source. Estimated object size is below 4 KB (.text about 2.5 KB, .data 0.3 KB, gCrashScreen .bss 2516 bytes). Adding it would stay under the 10 KB limit, but it would need new port code (fault bridge, ARM-to-MIPS context, blit). The link alone gives a dead thread that never fires.

### What the port already has (H02, docs/HISTORY.md lines 162-180)
- `pm_crash_install` (game thread and audio thread), `crash_handler` in `3ds/src/pm_main.c`: thread name, pc, lr, sp, far, fsr, cpsr, r0-r12, memory line, stack walk. Output through `pm_crash_line` and `crash_flush` (`3ds/src/pm_log.c`) to log.txt and crash.txt (append). `boot_fail` in `pm_mem.c` writes crash.txt before the heap exists.
- Tested on Azahar with `crashtest_call` and `crashtest_audio_call`. Real faults on hardware are NOT tested.
- The bottom screen shows boot errors (pm_gpu.c `pm_boot_error`). It does not show a crash.

## Decision
- Keep `crash_screen_init`, `is_debug_init`, `load_obfuscation_shims` and `crash_screen_set_draw_info` empty. They cover N64 hardware only (IS64 device, MIPS fault thread). This follows the shim rule: a shim stands in for real N64 OS or hardware, with no game logic.
- No slice is needed. Row S31 can move to docs/SLICES_DONE.md.
- Uncovered gap (not part of S31): a crash on hardware shows nothing on screen. The user must pull crash.txt with `pull-o` or `pull-n`. A port-layer "show the first CRASH line on the bottom screen" is possible after S28 proves the handler on hardware.

## Question for the user
Q-S31: Do you want the crash text (pc, lr, thread) drawn on the bottom screen from the H02 handler? Recommendation: no, not now. Wait for S28 hardware results. crash.txt already holds the data. If yes, it is a port-layer slice of about 1 KB with the libctru console, not the decomp crash screen.
