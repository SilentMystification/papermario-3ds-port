## How PaperBoat does 60 fps (facts from the files above)
- Game logic stays at 30 Hz. `gfxRetrace_Callback` still flips D_80073E0A (src/main.c:131-140, the same as this repo). Logic, input, scripts, animation, camera and collision run once per logic frame. Nothing in the game logic changes. Audio stays at one audio frame per 60 Hz retrace (docs/HISTORY.md, section "Widescreen and 60 fps research").
- Record: `Graphics_Retrace` calls `FrameInterpolation_StartRecord` before `gfxRetrace_Callback` and opens the child "game_logic". `port_nuGfxOnSubmit` calls `FrameInterpolation_StopRecord` on a task with NU_SC_SWAPBUFFER. One recording per logic frame goes into a ring of 8 slots.
- What is recorded: every `guMtxF2L(mf, m)` call adds a leaf (source MtxF, destination `Mtx*`). Leaves sit in a tree of nodes. A node opens with `FrameInterpolation_RecordOpenChild(a, b)` and closes with `RecordCloseChild`. The key of a node is the pair (a, b), for example ("model_matrix", TAG_MODEL(i, model)). The game files call these about 50 times (list below). The tag macros put the object ID or list index into the key.
- Pairing: a child of the new frame pairs with the child of the old frame that has the same key and the same occurrence index under the same parent. Leaves inside one node pair by their index. If the op sequence of a node differs between the two frames, the node pairs with itself (no lerp). A child with no old pair also pairs with itself.
- Interpolation: the FINAL matrices are lerped element by element: res = (1 - t) * old + t * new (`interpolate_mtxf`). The code comment says that a lerp of the inputs (angles, scale, positions) made rolling animations look wrong. The result is a map from the new-frame `Mtx*` address to the lerped MtxF. The interpreter uses the map entry in place of the matrix at that address.
- Frame order at 60 fps: `ProcessGfxCommands` draws the same display list two times per logic frame: first with t = 0.5 (lerp of frame N-1 and frame N), then with no replacement (frame N itself). So the true frame N is shown one 60 Hz frame later than at 30 fps.
- Overload: `RunCommands` skips the interpolated draw when the game has queued its next frame (`nuGfxTaskSpool >= 2`). Then only the key frame draws.
- Teleports: model.c `mdl_interp_epoch` adds an epoch to the node key when a model moves more than MDL_INTERP_TELEPORT_DIST (100.0f) in one frame. The key then has no old pair, so no lerp. snowfall.c keys each flake by its wrap epoch the same way.
- Camera cut: cam_main.c:359 calls `FrameInterpolation_DontInterpolateCamera` in camera init. At commit 282c269b no code reads the camera epoch. So the camera has no special cut rule in this commit.
- Screen-space rectangles: src/port/patches/ScreenAnchorPatches.cpp (77 lines) draws some texrects (shop prices, message popups) as quads under an ortho matrix inside a node, so they move with the interpolated world.
- The 180 degree "paper effect": the comment names it. The fix for actors (`RecordActorPosRotMatrix`, `has_adjusted`) is present but has no caller and its multiply is commented out. So PaperBoat shows the paper effect as it is.

## Port mapping (how this repo does the same)
- Logic: no change. `pm_frame_loop` (3ds/src/pm_main.c:246) already runs one game step every 2 vblanks (`PM_VBLANKS_PER_STEP 2`). Audio already runs per retrace (3ds/src/pm_audio.c). Input stays per step.
- Record hook: `guMtxF2L` (3ds/src/pm_gu.c:37) is the one place where the game writes an `Mtx`. It is the same hook as PaperBoat src/port/gu.c.
- Start and stop: `__wrap_step_game_loop` (3ds/src/pm_phase.c:171) or the draw call of `pm_gfx_retrace` (3ds/src/pm_nusys.c) starts the record. `nuGfxTaskStart` (3ds/src/pm_nusys.c:70) stops it.
- Draw: today `nuGfxTaskStart` calls `pm_gbi_run` at once in the draw iteration of `pm_frame_loop`, and the idle iteration draws nothing. With `fps60`: the draw iteration runs `pm_gbi_run` with t = 0.5 replacements. The idle iteration runs `pm_gbi_run` on the same saved list with no replacement (the key frame) and presents it. This is the PaperBoat order. The list stays valid: the idle retrace does not build a list (comment at pm_main.c:154-156).
- Replace: `load_mtx` (3ds/src/pm_gbi.c:1190) looks up the resolved `Mtx*` in the replacement table and loads the lerped float matrix in place of the N64 fixed point matrix.
- Store: PaperBoat uses std::unordered_map and vectors. The port uses flat arrays with the same keys and the same pairing rules: node id = hash(parent node id, a, b, occurrence index), leaf = (node id, leaf index, dest `Mtx*`, MtxF), and a per-node leaf count for the signature rule. This is a storage change only, not a method change.

## Memory (no cap, user decision 2026-10-18; report the size)
- Each slice reports the 3dsx size change in its commit and in PROGRESS.log.
- Estimate: code about 12 KB (pm_interp.c and about 50 one-line hooks). Data: 2 recordings x 4096 leaves x 76 B (node id, leaf index, dest, MtxF) = about 608 KB, plus a replacement table of 4096 x 68 B = about 272 KB. Total about 0.9 MB of heap. F06-1 measures the leaf peak. Size the tables to the peak plus 25 percent and report the number.
- No VRAM change. No new frame buffer.

## O3DS and N3DS cost (Azahar estimate, not hardware)
- One drawn frame in mac_00 costs about 21 ms today (GBI 11.1 ms, flush 7.4 ms, DrawArrays 2.2 ms, prep 0.6 ms). With `fps60` each logic frame draws two times.
- The O3DS (32 to 42 ms cpu per frame in heavy maps today) does not reach 60 fps. The overload skip (F06-5) keeps it at the 30 fps key frames. The toggle stays available on the O3DS (user decision 1).
- The N3DS can reach 60 fps only in light scenes before PO2 and PO3. S28 measures both consoles with `fps60 pacestat phase`.

## Risks
- BIGGEST: cost. The extra GBI walk doubles the CPU draw cost. Before PO2 and PO3, most scenes skip the extra frame and show 30 fps, and a scene near the limit can alternate between 30 and 60 (judder). Measure in S28.
- Pairing: an object with a node key that changes between frames gets no lerp (it moves at 30 fps). Objects drawn outside any node pair by index under the parent and can swap. The `f06 pair` log shows this.
- Side effects of the second pass: a frame grab, a render to image or a depth read back that runs two times can change what the game reads. F06-5 limits them to the key frame pass.
- Lag: the key frame shows one 60 Hz frame later than at 30 fps (16.7 ms more input lag). PaperBoat has the same lag.
- Paper flip at 180 degree turns: the lerp gives a thin sprite for one frame. PaperBoat has the same effect. Do not add a fix that PaperBoat does not have.
- Texture scrolls and texrects outside the anchor stay at 30 fps (no matrix). PaperBoat has the same limit.
