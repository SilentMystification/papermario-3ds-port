# F06 plan (planning only, 2026-10-18)

Research: docs/HISTORY.md section "Widescreen and 60 fps research". Rules: 3ds/AGENT_RULES.md. Each slice adds at most 10 KB of code. Model: sonnet per slice.

## Facts (from the code)
- The logic steps at 30 Hz: src/main.c:131-134 (D_80073E0A ^= 1), 3ds/src/pm_phase.c `__wrap_step_game_loop`.
- 3ds/src/pm_main.c `pm_frame_loop` paces with `PM_VBLANKS_PER_STEP 2`. 3ds/src/pm_gpu.c:699 `C3D_FrameBegin(C3D_FRAME_SYNCDRAW)` waits for one vblank.
- Audio is already one frame per 60 Hz retrace (3ds/src/pm_audio.c:144-155). F06 does not touch audio.
- Matrices enter at 3ds/src/pm_gbi.c `load_mtx` (line 1011) and `upload_mvp` (line 213). Stack `mv[10]`, `mv_sp`, `proj`.
- Cost of one drawn frame in mac_00 (PT01, Azahar, fast run): GBI interpret 11.1 ms + draw prep 0.6 ms + flush 7.4 ms + DrawArrays 2.2 ms = 21.3 ms. The budget of one 60 Hz frame is 16.7 ms for everything.

## Method (inference)
Keep the logic at 30 Hz. After step N draws frame N, the loop draws one extra frame N-1/2 in the free vblank. The extra frame walks the same display list of frame N again. Each G_MTX matrix is replaced by lerp(matrix of frame N-1, matrix of frame N, 0.5) for the same key. A matrix with no key match uses the frame N matrix. The display list stays valid: the game builds the next list into the other display context, and the game thread does not run during the extra draw.
Key of one matrix: the address of the first G_VTX or G_DL target after the G_MTX (static model data, the same address every frame) plus the occurrence count of that address in the frame. Paperboat used an explicit tree (FrameInterpolation.cpp, 744 lines). Use the address key first. Change to a tree only if slice F06-3 measures a low match rate.
Drop to 30 fps at once when the CPU time of the last step plus two draws is above 33 ms (adaptive policy of soh-3ds).

## Conflicts with the graphics rows
- pm_gbi.c (`load_mtx`, the display list walk): B1, B2, B3, B5, B6, F08, V10, V13 all edit pm_gbi.c. F06-2, F06-3, F06-5 start only after all of them are done.
- Frame grabs (B2 role T2, B5 z-buffer, F03 depth readback, X02 darkness): the extra frame must not grab again or write N64 memory. F06-5 checks each one in the render_gaps.md list.
- pm_gpu.c FrameBegin/FrameEnd: F06-3 calls them one more time per step. B1-B3 use offscreen slots per frame. Check that the slot reuse in pm_gpu.c does not assume one frame per step.
- PO3 (docs/plans/PO3_row.md): PO3 moves the vertex transform to the PICA vertex shader with the matrix as a uniform. This is good for F06: the extra frame then costs a uniform upload and the draw, not a CPU transform. Do F06-3 after PO3, or write `pm_gbi_redraw` so that it only changes the matrix upload (`upload_mvp`). Both rows edit `upload_mvp` and `load_mtx`. Run them one at a time.
- PO2 and PO1 (flush per draw) cut the 7.4 ms flush. F06 needs them.

## Risks
- Key mismatch: objects that appear or leave in one step get the frame N matrix. Objects that share one vertex address (many NPCs with one model) can swap keys if the draw order changes. The match rate log in F06-2 shows this.
- The extra frame doubles GBI and GPU work. On the O3DS it does not fit (see below). On the N3DS it fits only after PO1, PO2, PO3.
- One frame of input lag at 60 fps (the midpoint frame shows the past).
- Camera cut threshold: too low gives judder, too high gives one smeared frame at cuts.

## O3DS cost (estimate from Azahar, not hardware)
- One extra frame costs about 21 ms in mac_00 today. The O3DS needs at most 16.7 ms per drawn frame for 60 fps. Today one O3DS frame is estimated at 32 to 42 ms cpu (PT01, kmr_20 36 ms). Result: 60 fps is NOT possible on the O3DS. The adaptive drop keeps it at 30 fps, so the toggle must be N3DS only or off by default on the O3DS (check `APT_CheckNew3DS`).
- N3DS: possible only if PO1, PO2, PO3 bring one draw to about 6 ms. Measure in S28 first.

## Memory estimate
- Matrix record: 2 frames x 1024 entries x (16 floats + key 8 B) = 2 x 1024 x 72 B = 144 KB of heap. This is above the 10 KB slice rule for data. Ask the user before F06-2 (3ds/QUESTIONS.md). Fallback: store s16 fixed point (32 B + 8 B) = 80 KB. O3DS spare is about 4.7 MB (docs/MEMORY_BUDGET.md), so it fits.
- No VRAM change. No new frame buffer.
