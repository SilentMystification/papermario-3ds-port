# papermario-3ds-port rules

Orchestrator sessions: read docs/handoff/orchestrator_rules.md at the start. Code agents: read your row file (docs/handoff/row_<id>.md) first. The rules below apply to everyone.

5. TESTS: run tests through the bench CLI, the entry point: `python 3ds/tools/bench.py run <bench> --row <row> --why "<text>"` (`bench.py list` shows the benches, `bench.py show <bench>` the recipe and gates). Benches, recipes, gates and results are in 3ds/tools/bench_defs.json, 3ds/logs/perf/runs.jsonl and docs/handoff/test_catalog.md. Do not hand-build run_azahar.ps1 commands for a test a bench covers. A new scenario is added to azt_scenarios.json and a new bench to bench_defs.json in the same commit. Set PM_ROW=<row> in every test shell.
   - SCOPE: a row is tested only against what it can change. The row names its affected scenarios before it starts. No regression sweep, no catalog run per row, no baseline-build comparison unless the row changes pixels in that scene. Data-only change (ROM image, assets): boot and memory line, one heavy map, the scene that uses the data. Only a change to shared draw code (pm_gbi.c, pm_gpu.c, pm_tex.c, src/model.c) needs a byte-equal check, and only on scenes that use the changed path. A full test (whole catalog or 411-map run) runs only when an epic merges and only if valuable for that epic. For any other full test, ask the user. No statehash runs. No golden.py runs (user decisions).
   - TIME: no test idles. A test ends within 5 s of its until-line. Every scenario has a cap (subject time plus 5 s; most 10 to 25 s; 45 s upper limit; longer only with a stated reason in the scenario for a soak or long measurement). azt.ps1 refuses a scenario without a cap and an until-line the build prints. No waiting in a menu or an empty scene.
   - JUSTIFICATION FIRST: before each Azahar start, write one line to 3ds/logs/perf/status_<row>.txt: the quantity the run measures, the code path it tests, and why no other run answers it. No line, no start.
   - BUDGET: 8 Azahar starts per row, 3 for a diagnostic row. It only stops repeats of the same shot and never blocks work. At the cap with gates unrun: report the row INCOMPLETE, reset (`powershell -NoProfile -File 3ds/run_azahar.ps1 -ResetBudget <row>`), continue. Never drop a row or skip a gate because the budget ended. Drop a row only when a valid gate ran and failed.
   - PASS: a pass includes the picture, and the shot must show the subject. Fault counters at 0 are not a pass. The until-line is a log event for that subject. A frame window chosen before the log shows the event is not a test: take another window on the same binary. One quantity per shot. If the picture does not show that quantity change, discard the edit. A new file and line for the same claim is the same experiment. Two unchanged shots of that quantity end the edit series. The next diagnosis names the value the draw used.
   - Agents grep and read line ranges, write tool output to files, and write status lines to 3ds/logs/perf/status_<row>.txt.
7. CODE: after each finished piece of work, commit (changed files only, never 3ds/src/map_restore_table.c). No feature toggles: a finished implementation replaces the main path and the same row deletes the old path. Debug tools may stay. No stubs. No git push. No Claude attribution in commits. Untested code goes on a branch. When the shot shows the quantity changed, commit before the next stage. When it does not, revert those files before the next stage. A diagnosis that names a line already in the binary of the failed shot does not start a code agent. Commit docs after every group of rows. All code follows docs/handoff/hw_guidelines.md (3DS cache and ARM11 rules: hot loops fit the 16 KB L1I and L1D, tight data, no division, no double, sequential access, one flush per split).
9. PLATFORM: Windows. Use repo-relative paths, the .ps1 tools, and Git Bash for sh tools (push_3ds.sh, build.sh, sweep.py). Newest information wins over old docs. The user file 3ds/src/map_restore_table.c is never committed and never discarded. Run python 3ds/tools/gen_map_restore.py before a build, then restore that file.
