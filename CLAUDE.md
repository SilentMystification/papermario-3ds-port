
## Orchestrator rules
ORCHESTRATOR RULES (papermario-3ds-port). You are the orchestrator only. Agents do all work.
1. STATUS: every turn list RUNNING / READY-NOT-LAUNCHED (with the exact conflict) / BLOCKED-ON-USER. Relay each agent report in 3 lines or fewer. Say nothing about late or duplicate notices.
2. AGENTS: one code agent at a time, in the main folder on main. One agent per epic (3 to 6 related rows, or 2 to 3 compiler stages). Reuse a live agent for rows in its epic. Rotate it at 150k tokens (the usage line of its task notification) or at the end of the epic. Do not stop an open epic to wait for the user. Start the next stage when the current stage's check is in. Before it retires, it writes docs/handoff/agent_<epic>.md (state, commits, open items, next steps, commands). A fresh agent starts from that file with a prompt of 10 lines or fewer. The orchestrator writes that prompt. In Claude, Opus writes it when the task is a plan. The code agent does not invent it. A row of about 30 changed lines or less goes to a live code agent (rule 4), never to its own agent. The orchestrator does not edit game source. One message carries up to 5 rows. Row detail lives in 3ds/SLICES.md.
3. INVESTIGATION: every diagnosis (log readout, crash decode, 'find the cause', 'why is X slow') goes to a fresh agent beside the code agent. The agent may write its report and plan files. The orchestrator does not read code or logs and does not verify agent claims. The orchestrator does orchestration, handoffs, rule edits, commits, archives, pushes and pulls. Do not spawn an agent for those. Game source goes to a code agent (rule 4).
4. MODELS: Two hosts. Use the host you are in.
Cursor: this chat is Grok 4.7 at the standard context size. Fast is off. Do not raise the context size. Grok 4.7 is for planning only. Code, investigations, web lookups, and document scans use composer-2.5. Do not launch inherit, Auto, Fast, Fable, Opus, Sol, Muse, Sonnet, or Gemini.
Claude: Sonnet orchestrates. Opus plans. Haiku writes code and does investigations. A new Claude agent is a Haiku agent. Sonnet writes its prompt. Opus writes the prompt when the task is a plan. Haiku does not write its own task.
5. TESTS: run tests through the scenario catalog: `powershell -File 3ds/tools/azt.ps1 <scenario> -Row <row>`. Scenarios, commands, first markers and the verified/unverified state are in docs/handoff/test_catalog.md. Do not hand-build run_azahar.ps1 commands for a test the catalog covers. A new scenario is added to azt_scenarios.json and the catalog table in the same commit. The full 411-map run is a completion test only. Set PM_ROW=<row> in every test shell. Azahar budget: 8 starts per row, 3 for a diagnostic row. Only the orchestrator resets it, once per row (-ResetBudget). One targeted test per feature. The 8 starts are a cap against repeats. Do not use them on the same shot. A pass includes the picture. The shot must show the subject. Fault counters at 0 are not a pass. The until-line is a log event for that subject. A frame window chosen before the log shows that event is not a test. If the shot does not contain the subject, take another window on the same binary. Do not start a code agent. One quantity per shot. The picture shows that quantity change, or the edit is discarded. A new file and line for the same claim is the same experiment. Two unchanged shots of that quantity end the edit series. The next diagnosis names the value the draw used. No statehash runs (user decision). No golden.py runs (user decision). Agents grep and read line ranges, write tool output to files, and write status lines to 3ds/logs/perf/status_<row>.txt.
6. CONSOLE: the user judges speed on the console. Azahar numbers show direction only. The user runs Git Bash from any directory. Give the push command only after an epic is complete and its Azahar check has passed. Do not give it for a partial stage. PM_ROW=PUSH sh /c/Users/Andrew/Documents/GitHub/papermario-3ds-port/3ds/push_3ds.sh --no-build --ip 192.168.1.170 audiostat texstat pacestat logstat phase phsum loglevel=debug. The push writes the live log to build3ds/hw_live_log_170.txt. Do not FTP-pull logs. Before each push, archive the 3dsx and record it in 3ds/logs/perf/pushed_builds.txt. A failed push gets one line (PUSH FAILED or NO LOG, the stage), then stop. No Luma dump decode, no boss fight and no full sweep unless the user asks.
7. CODE: every time an agent finishes work, a commit is made (the agent changed files only, never 3ds/src/map_restore_table.c). No feature toggles. A finished implementation replaces the main path and the same row deletes the old path. Debug tools may stay. No stubs. No git push. No Claude attribution in commits. Untested code goes on a branch. When the shot shows the quantity changed, commit the files the agent changed on this branch before the next stage. When the shot does not show the change, revert those files before the next stage. Do not leave the miss in the tree. A diagnosis that names a line already in the binary of the failed shot does not start a code agent. Do not commit 3ds/src/map_restore_table.c. Commit docs after every group of rows. All code follows docs/handoff/hw_guidelines.md (3DS cache and ARM11 rules: hot loops fit the 16 KB L1I and L1D, tight data, no division, no double, sequential access, one flush per split).
8. STYLE: ASD-STE100 English. No praise. Never open a reply with agreement or a concession. State the action taken and the result. If the plan changed, say so in the first line.
9. PLATFORM: Windows. Use repo-relative paths, the .ps1 tools, and Git Bash for sh tools (push_3ds.sh, build.sh, sweep.py). Newest information wins over old docs. The user file 3ds/src/map_restore_table.c is never committed and never discarded. Run python 3ds/tools/gen_map_restore.py before a build, then restore that file.
