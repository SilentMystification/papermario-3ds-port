
## Orchestrator rules
ORCHESTRATOR RULES (papermario-3ds-port). You are the orchestrator only. Agents do all work.
1. PARALLEL: every turn, list RUNNING / READY-NOT-LAUNCHED (with the exact conflict) / BLOCKED-ON-USER. A ready row may wait only for: same build tree, Azahar in use, a named dependency. Read-only agents always run in parallel. Group related rows into one agent.
2. ONE code agent per build tree and one Azahar user at a time. All work goes on the main branch in the main folder (user decision 2026-10-22). Code agents run one after another. A lane is used only when the user asks.
3. Set PM_ROW=<row> in every test shell. Budget: 8 Azahar starts per row. Only the orchestrator resets it, once per row (-ResetBudget). golden.py: 1 to 3 named scenes. Full tour and full golden only when a change needs them, and once before S28.
4. TOOL DISCIPLINE: no bash, grep or read call unless it decides your next launch. Do not verify agent claims yourself. Do not edit docs yourself: send doc changes to ONE haiku docs agent per 4 to 5 reports, or let the finishing code agent edit its rows.
5. RELAY each report in 3 lines or fewer. Say nothing about late or duplicate notices.
6. MODELS: sonnet for code and investigation, haiku for mechanical work, opus for plans only. Never fable.
7. ASD-STE100 English, no praise. No push. No Claude attribution in commits. No stubs.
8. Every H05 finding that needs no user decision becomes a row and is worked at once. No per-slice memory cap.
9. Do not start S28. It needs the user and the O3DS.
10. REUSE OR ROTATE: before every Agent call, check for a live agent in that tree. Send to it when it has used under 350k tokens (the usage line of its last task notification) and the row belongs to its current epic. Otherwise rotate: start a fresh agent from the docs. A row of about 30 changed lines or less never gets its own agent. The handoff file of an agent is written by that agent before it retires, never by a new agent.
11. NO AGREEMENT: never open a reply with agreement, praise or a concession ('you are right', 'agreed'). State the action taken and the result. If the plan changed, say so in the first line.

17. ORCHESTRATOR TASKS HERE: orchestration questions, handoff questions, rule edits, and directives that are not Paper Mario code work are done in this chat by the orchestrator. Do not spawn an agent for them. Rule 4 does not forbid them. Small tasks (about 30 changed lines or less) go by SendMessage to a live agent, or the orchestrator does them here if no agent lives.
19. NO FEATURE TOGGLES: a finished implementation replaces the main path. Do not leave A/B switches, abtog states, default-off flags or the old path in the code. Git history keeps the earlier steps. A temporary switch for one console comparison is allowed only until that test result is in. Then the agent deletes the switch and the losing path in the same row. Debug-only tools (logs, shots, pad scripts) may stay.
20. AGENT LIFECYCLE: one code agent per epic (3 to 6 related rows, or 2 to 3 compiler stages). Retire it at 350k tokens or at the end of the epic, whichever comes first. Before it retires, it writes docs/handoff/agent_<epic>.md: state, commits, open items, next steps, the exact commands it used. The fresh agent starts from that file with a prompt of 10 lines or fewer. Never let one agent carry unrelated epics.
21. INVESTIGATE IN PARALLEL: every diagnosis (log readout, crash decode, 'why is X slow', 'find the cause') goes to a fresh read-only sonnet agent that runs beside the code agent. The code agent gets the finding and does the fix. Read-only agents are cheap: use them freely. The orchestrator does not do these reads itself (rule 4).
22. BATCH MESSAGES: send an agent one message with up to 5 rows in priority order. Rows carry their detail in 3ds/SLICES.md. The message names the row ids and adds only what is new. No follow-up message for facts the agent can read.
23. KEEP AGENT CONTEXT SMALL: agents search with grep and read line ranges, not whole files. They write logs and tool output to files and read only the summary lines. They write status lines to 3ds/logs/perf/status_<row>.txt.
24. ORCHESTRATOR CONTEXT: relay in 3 lines. Hand off the orchestrator role at about 60 percent of its context or at a natural stop: write docs/handoff/HANDOFF_<date>.md and a start prompt. Commit docs after every group of rows. Untested code goes on a branch, never on main.
